About

What FrameLabs is

FrameLabs is a capture app for stop-motion animation that opens directly into Blender, with the camera, timeline, and image sequence already set up.

Why it exists

Most stop-motion capture tools stop at the camera: you shoot your frames, then manually export, organize folders, and rebuild the scene in Blender by hand.

FrameLabs handles that handoff. You capture a frame, and it writes the image, generates a thumbnail, updates the timeline, and — when you're ready — builds the Blender scene for you.

Workflow

  1. Connect a camera: FrameLabs detects webcams and tethered DSLR/mirrorless cameras on startup (libcamera support is planned, see Roadmap).
  2. Capture a frame: Press Space. The frame is verified, saved as PNG, thumbnailed, and added to the timeline in under a second.
  3. Review on set: Onion skin, a histogram, and safe-area guides are available while shooting.
  4. Open in Blender: One button saves the project, launches Blender, and builds the scene — camera, image sequence, compositor, and output settings.
License

Free and open source

FrameLabs is licensed under GPL-3.0. Development happens in the open — code, tests, and roadmap status are all public.

Design principle

Captured frames aren't replaceable

UI operations run in background workers so the interface doesn't block. Autosave runs after every capture. Timeline edits have at least 100 steps of undo history.

Platforms

Windows, macOS, Linux

Built on Python 3.12+ and PySide6. Targets 60 FPS UI and 30+ FPS live preview on all three.

DONE▾

Capture workflow

  • Timeline updates immediately; no duplicate frame numbers

  • Disk full → "Disk Full / Capture Aborted" — the project stays usable
  • Write failure retries once, then shows an error

Developer handbook

Developer documentation

The Developer Handbook is the source of truth for implementation decisions — if code conflicts with it, the handbook wins. Here's the shape of it.

Guiding principles

Every design decision reinforces these.

01

Never Lose User Data

A captured frame is the most valuable thing in the app. Nothing — a crash, a disconnect, a failed export — should ever lose one. If there's uncertainty, preserve the data.

02

UI Never Blocks

Saving, importing, exporting, thumbnailing, and launching Blender all run on background workers. The interface stays responsive, always.

03

Small Modules

Each module does one thing. CaptureService, not CaptureManagerThatAlsoHandlesUISavingExportsAndPlayback.

04

Explicit Over Clever

Readable beats clever. No unnecessary abstraction, no hidden behavior — clarity first.

05

Composition Over Inheritance

Objects are assembled from smaller services rather than built through deep inheritance hierarchies.

UI never touches hardware or the filesystem directly — everything routes through services and the event bus.

Camera interface

Every backend — webcam, gphoto, libcamera — implements the same contract. The rest of the app never knows which is connected.

  • disconnect()

  • stop_live_view()

Capture pipeline

A fixed sequence — never reordered without justification.

  • Trigger camera
  • Receive image
  • Verify image
  • Write image + metadata
  • Generate thumbnail
  • Update timeline
  • Autosave
  • Emit FRAME_CAPTURED

Event bus

Modules talk through events, named in past tense — they describe something that already happened.

FRAME_CAPTURED PROJECT_OPENED PROJECT_SAVED TIMELINE_UPDATED CAMERA_CONNECTED CAMERA_DISCONNECTED PLAYBACK_STARTED BLENDER_SYNC

Project file format

Projects are plain folders. No proprietary binary formats — project.ffproj is readable, versioned JSON.

{
  "version": 1,
  "name": "Robot Walk Cycle",
  "fps": 12,
  "resolution": [6000, 4000],
  "camera": { "model": "Canon EOS R50", "lens": "50mm" },
  "frames": [ { "number": 1, "file": "images/000001.png" } ]
}
